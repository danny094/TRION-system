# TRION Operation Contract: Ironclad Control for AI Agents

In most AI agent systems, the Large Language Model (LLM) is given direct access to a set of tools. The LLM analyzes the user prompt and decides which tool to run and with what arguments. While flexible, this approach is dangerous:
* **Hallucinated parameters:** The LLM might invent arguments (e.g., trying to access a container ID that doesn't exist).
* **Prompt injections:** A clever user can trick the LLM into executing destructive actions (e.g., deleting a database or spawning an unauthorized server).
* **Infinite loops:** If a tool fails, the LLM might repeatedly call the same failing tool with the same arguments, burning through API tokens without making progress.

TRION solves this by inserting a strict gatekeeper: the **Operation Contract**.

---

## What is an Operation Contract?

The Operation Contract is a formal, immutable agreement generated by TRION *before* the agent starts planning or executing tools. It defines exactly:
1. **The Domain:** Which subsystem is targeted (e.g., `container_runtime`, `file_system`).
2. **The Primary Operation:** The single permitted activity (e.g., `list`, `inspect`, `write`, `execute`).
3. **The Target:** The specific container, file, or resource allowed to be touched.
4. **The Required Evidence:** The exact data output the agent must gather to consider the task complete.

Once this contract is generated, **it cannot be changed**. Even if the LLM tries to run a different tool or modify a container in the background, TRION's execution engine will physically block the action because it violates the contract.

```
User Input ──► [ TMR (Meaning) ] ──► [ Operation Contract ] ──► [ Safe Execution Gate ]
                                                                       │
                                           Locked down to:             ▼
                                        - Allowed tools only     [ Tool Executor ]
                                        - Allowed arguments only
```

---

## Decoupling Meaning from Action

The core architectural rule of TRION is:
> **`meaning != operation`**
>
> What the user *means* is not the same as what the agent is *authorized* to do.

For example, when a user asks: *"What is running at home?"*, TMR extracts the meaning: `runtime_state` of the `container` theme in the `home` scope.

The Operation Contract then maps this meaning to the **`list`** operation. 
* Under the `list` operation, **only read-only listing tools** (like `container_list`) are allowed.
* Advanced details or modifications (like `container_inspect` or `container_delete`) are **strictly locked out** for this request. The agent cannot bypass this restriction, even if it runs into an error.

## Key Benefits for Users

> [!TIP]
> **Zero Trust Agent Execution**
> With the Operation Contract, you don't need to "trust" the LLM to behave safely. The core engine mathematically enforces safety boundaries before the LLM can touch your system.

* **Fail-Closed Security:** If a tool call lacks required arguments or attempts to perform an action outside the approved operation, it is immediately blocked.
* **No Endless Error Loops:** The **Run Governor** sets strict, global budgets for steps, replans, and time. If the agent gets stuck, it is terminated cleanly instead of looping infinitely.
* **Predictable Outcomes:** Because the expected output (evidence) is defined in the contract, the agent only finishes when it has gathered the actual facts, preventing false "success" reports.
